## 📋 执行摘要

本报告全面回顾了AI知识库管理平台的需求、目标和预期成果，并基于**子项目0（用户中心）已完成**的实际情况以及**最新架构调整决策**，对技术方案进行了全面更新。

### 🔄 重大架构调整 (v2.0 → v3.0)

#### 调整1: 租户隔离策略变更 ⭐ 关键变更
- **v2.0方案**: Schema级物理隔离（每个租户独立Schema）
- **v3.0方案**: 字段级逻辑隔离（tenant_id字段）
- **变更理由**: 简化架构，降低复杂度，提高灵活性

#### 调整2: 知识库业务模型变更 ⭐ 关键变更
- **v2.0方案**: 知识库归属于租户（租户独占）
- **v3.0方案**: 知识库作为资源，可添加到租户（多对多关系）
- **变更理由**: 支持知识库共享，租户可同时利用多个知识库

#### 调整3: 与子项目0集成深度 ⭐ 关键变更
- **v2.0方案**: 依赖子项目0提供认证和权限
- **v3.0方案**: 充分利用子项目0所有能力，杜绝重复造轮子
- **变更理由**: 避免重复建设，统一管理

### 核心发现

✅ **方案可行性**: 基于WeKnora框架的技术方案成熟可行
✅ **架构优化**: 逻辑隔离方案更简单，开发周期进一步缩短至5-6周
✅ **风险降低**: 逻辑隔离实现更简单，风险更低
⭐ **业务模型**: 知识库资源模型更灵活，支持共享和协作

## 2. 知识库改造目标

### 2.1 核心改造目标

#### 目标1: 基于WeKnora的多租户化 ⭐ 主要目标（调整）

**改造前**: WeKnora是单租户知识库系统
**改造后**: 支持多租户的企业级知识库平台

**具体改造** ⭐ 架构调整:

1. **数据层改造** ⭐ 重大调整
   - 采用**字段级逻辑隔离**策略（tenant_id）
   - 所有表增加tenant_id字段
   - SQL查询自动添加 `WHERE tenant_id = ?`
   - **不存储用户数据**（由子项目0管理）
   - **不存储租户数据**（由子项目0管理）

2. **知识库资源模型** ⭐ 新设计
   - 知识库作为独立资源
   - 知识库有所有者（owner_id，来自子项目0）
   - 知识库可被添加到租户（多对多关系）
   - 租户-知识库关联表管理访问权限

   ```
   知识库（全局资源）
       ↓
   租户A ← 添加 → 知识库1
   租户A ← 添加 → 知识库2
   租户B ← 添加 → 知识库1  # 共享
   租户B ← 添加 → 知识库3
   ```

3. **API层改造**
   - 所有API增加租户上下文
   - 自动从JWT Token提取tenant_id和user_id
   - 所有查询自动过滤tenant_id
   - **知识库查询API返回租户下的所有知识库**
   - **检索API自动检索租户下所有知识库**

4. **认证授权改造** ⭐ 完全依赖子项目0
   - **零本地认证代码**
   - Token验证：调用子项目0 API
   - 权限校验：调用子项目0 RBAC API
   - 用户信息：调用子项目0 API获取
   - 租户信息：调用子项目0 API获取
   - 本地缓存降低延迟

5. **前端改造**
   - 移除本地登录页面
   - 跳转到子项目0统一登录
   - Token管理（存储、刷新、过期处理）
   - 显示租户上下文信息
   - **显示租户下的知识库列表**
   - **支持添加/移除知识库**

#### 目标2: 保留WeKnora核心能力 ⭐ 重要目标

**保留能力**:
- ✅ 文档解析引擎（PDF/Word/Markdown/图像）
- ✅ 多种向量化模型支持（BGE/GTE/本地模型）
- ✅ 混合检索策略（BM25 + 密集向量 + GraphRAG）
- ✅ RAG问答能力（思维链模式）
- ✅ 知识图谱构建（可选）

**改造策略**:
- **最小侵入**: 只改造数据访问层，不修改核心算法
- **功能增强**: 在WeKnora基础上增加企业级功能
- **版本管理**: Fork仓库独立维护，定期同步上游更新

#### 目标3: 与SalesChampionHub生态集成 ⭐ 战略目标

**集成点**:

1. **与子项目0深度集成**（认证授权、租户管理、用户管理）
   - 统一身份认证入口
   - 统一权限管理
   - 统一审计日志
   - **统一租户管理**
   - **统一用户管理**
   - **杜绝重复造轮子**

2. **为下游服务提供API**（子项目3、7等）
   - 标准REST API
   - 基于Token的认证

## 3. 新数据模型设计

### 3.1 核心数据模型 ⭐ 全新设计

#### 模型1: 知识库（全局资源）

```sql
CREATE TABLE knowledge_bases (
    id VARCHAR(50) PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    description TEXT,
    owner_id VARCHAR(50) NOT NULL,  -- 创建者（来自子项目0）
    visibility VARCHAR(20) DEFAULT 'private',  -- public/private/shared
    tags TEXT[],
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW(),
    settings JSONB DEFAULT '{}',

    INDEX idx_kb_owner (owner_id),
    INDEX idx_kb_visibility (visibility),
    INDEX idx_kb_created (created_at)
);

-- visibility说明:
-- public: 所有租户可见和添加
-- private: 仅创建者所在租户可见
-- shared: 通过邀请添加到其他租户
```

#### 模型2: 租户-知识库关联（多对多）⭐ 核心表

```sql
CREATE TABLE tenant_knowledge_bases (
    id BIGSERIAL PRIMARY KEY,
    tenant_id VARCHAR(50) NOT NULL,  -- 租户ID（来自子项目0）
    kb_id VARCHAR(50) NOT NULL REFERENCES knowledge_bases(id) ON DELETE CASCADE,
    added_by VARCHAR(50),  -- 添加者（来自子项目0）
    added_at TIMESTAMP DEFAULT NOW(),
    permissions JSONB DEFAULT '{"can_read": true, "can_write": false, "can_delete": false}',
    is_active BOOLEAN DEFAULT true,

    UNIQUE (tenant_id, kb_id),
    INDEX idx_tenant_kb_tenant (tenant_id),
    INDEX idx_tenant_kb_kb (kb_id),
    INDEX idx_tenant_kb_active (tenant_id, is_active)
);

-- 这个表决定了:
-- 1. 哪些知识库属于哪些租户
-- 2. 租户对知识库的权限
-- 3. 用户查询时会检索租户下所有 is_active=true 的知识库
```

#### 模型3: 文档（属于知识库）

```sql
CREATE TABLE documents (
    id VARCHAR(50) PRIMARY KEY,
    kb_id VARCHAR(50) NOT NULL REFERENCES knowledge_bases(id) ON DELETE CASCADE,
    file_name VARCHAR(255) NOT NULL,
    file_type VARCHAR(50),
    file_size BIGINT,
    uploader_id VARCHAR(50) NOT NULL,  -- 上传者（来自子项目0）
    content TEXT,
    vector_id VARCHAR(255),  -- 向量数据库中的ID
    version INT DEFAULT 1,
    status VARCHAR(20) DEFAULT 'processing',  -- processing/ready/failed
    metadata JSONB DEFAULT '{}',
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW(),

    INDEX idx_doc_kb (kb_id),
    INDEX idx_doc_status (kb_id, status),
    INDEX idx_doc_uploader (uploader_id)
);
```

#### 模型4: 向量数据（pgvector）

```sql
CREATE TABLE vectors (
    id BIGSERIAL PRIMARY KEY,
    document_id VARCHAR(50) NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    chunk_index INT NOT NULL,
    chunk_text TEXT,
    embedding vector(1536),  -- 向量维度根据模型调整
    metadata JSONB DEFAULT '{}',

    INDEX idx_vector_doc (document_id),
    INDEX idx_vector_embedding ON vectors USING ivfflat (embedding vector_cosine_ops)
);
```

#### 模型5: 查询日志（用于分析和计费）

```sql
CREATE TABLE query_logs (
    id BIGSERIAL PRIMARY KEY,
    tenant_id VARCHAR(50) NOT NULL,  -- 租户ID
    user_id VARCHAR(50) NOT NULL,    -- 用户ID
    kb_ids TEXT[],  -- 查询涉及的知识库列表（数组）⭐ 关键
    query_text TEXT,
    query_type VARCHAR(20),  -- search/ask
    result_count INT,
    latency_ms INT,
    created_at TIMESTAMP DEFAULT NOW(),

    INDEX idx_query_tenant (tenant_id, created_at),
    INDEX idx_query_user (user_id, created_at)
);

-- 按月分区（数据量大）
CREATE TABLE query_logs_2025_11 PARTITION OF query_logs
    FOR VALUES FROM ('2025-11-01') TO ('2025-12-01');
```

### 3.3 典型业务场景

#### 场景1: 用户查询问题

```sql
-- 1. 从JWT Token获取 tenant_id 和 user_id
-- 2. 获取租户下的所有知识库
SELECT kb_id FROM tenant_knowledge_bases
WHERE tenant_id = 'tenant_001' AND is_active = true;

-- 3. 在这些知识库中检索文档
SELECT d.* FROM documents d
WHERE d.kb_id IN ('kb_001', 'kb_002', 'kb_003')
AND d.status = 'ready';

-- 4. 向量检索（跨多个知识库）
SELECT v.* FROM vectors v
JOIN documents d ON v.document_id = d.id
WHERE d.kb_id IN ('kb_001', 'kb_002', 'kb_003')
ORDER BY v.embedding <=> '[query_vector]' LIMIT 10;

-- 5. 记录查询日志
INSERT INTO query_logs (tenant_id, user_id, kb_ids, query_text)
VALUES ('tenant_001', 'user_123', ARRAY['kb_001', 'kb_002', 'kb_003'], '销售技巧');
```

```sql
-- 1. 验证用户权限（调用子项目0）
-- 2. 添加知识库到租户

VALUES ('tenant_001', 'kb_123', 'user_456');

-- 3. 该租户的所有用户现在可以检索这个知识库
```

```sql
-- 租户B也添加（共享）
INSERT INTO tenant_knowledge_bases (tenant_id, kb_id)
VALUES ('tenant_B', 'kb_shared');

-- 两个租户都可以检索这个知识库
-- 但只有owner可以修改知识库本身
```

#### 字段级租户隔离 ⭐ 架构调整

**选择理由**: ✅ 简化架构

#### 风险2: 数据隔离风险 ⚠️ 中风险（新增）

**风险描述**: 字段级隔离可能导致误操作跨租户访问

**影响范围**: 数据安全

**发生概率**: 低（通过技术手段防范）

- ✅ **代码审查**: 严格审查所有数据访问代码
- ✅ **自动化测试**: 跨租户访问测试用例
- ✅ **监控告警**: 异常跨租户访问告警

**数据库RLS示例**:
```sql
-- 启用RLS
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

-- 创建策略
CREATE POLICY tenant_isolation_policy ON documents
USING (
    kb_id IN (
        SELECT kb_id FROM tenant_knowledge_bases
        WHERE tenant_id = current_setting('app.current_tenant')::text

);
```

**评估**: ✅ 风险可控，有多层防护

**风险描述**: 多知识库联合查询可能影响性能

- ✅ **查询优化**: 限制联合查询的知识库数量（如最多10个）
- ✅ **Redis缓存**: 缓存租户-知识库关联
- ✅ **分页**: 大结果集分页返回

## 6. 优化建议

### 6.1 架构优化建议

#### 建议1: 实施数据库RLS ⭐ 高优先级（新增）

**建议**: 使用PostgreSQL的Row Level Security作为双重保障

**优势**:
- ✅ 数据库层面强制隔离
- ✅ 即使应用代码有bug也能保护数据
- ✅ 与字段级隔离完美配合

**实施**:
```sql
-- 所有租户相关表启用RLS
ALTER TABLE knowledge_bases ENABLE ROW LEVEL SECURITY;
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

-- 创建策略
CREATE POLICY tenant_access ON documents
USING (kb_id IN (
    SELECT kb_id FROM tenant_knowledge_bases
    WHERE tenant_id = current_setting('app.current_tenant')::text
));
```

**影响**: 增加1-2天开发时间，但安全性大幅提升

#### 建议2: 知识库数量限制 ⭐ 高优先级

**建议**: 限制单次查询涉及的知识库数量

**理由**:
- 联合查询知识库过多会影响性能
- 用户一般不需要同时查询太多知识库

**实施**:
- 单次查询最多10个知识库
- 超过限制返回错误或智能选择（根据相关性）

**影响**: 性能可控

#### 建议3: 文档处理异步化 ⭐ 高优先级

**建议**: 使用消息队列（RabbitMQ/Redis Queue）异步处理

**优势**:
- ✅ 用户体验更好（上传立即返回）
- ✅ 系统吞吐量更高
- ✅ 处理失败可重试

**实施**: Week 3实施

#### 建议4: 分层缓存策略 ⭐ 高优先级

**分层设计**:
1. **L1缓存**: 应用内存缓存（租户-知识库关联）
2. **L2缓存**: Redis缓存（用户信息、查询结果）

**实施**: Week 4实施

**影响**: 响应时间降低30-50%

### 6.2 功能增强建议

#### 建议5: 知识库推荐功能 ⚠️ 中优先级

**建议**: 根据查询内容智能推荐相关知识库

**功能**:
- 分析用户查询
- 推荐可能相关的公共知识库
- 租户可一键添加

**实施**: v1.1版本

#### 建议6: 知识库分析仪表板 ⚠️ 中优先级

**建议**: 提供知识库使用分析

**功能**:
- 知识库访问统计
- 热点文档排行
- 多知识库查询分布

**实施**: v1.1版本
